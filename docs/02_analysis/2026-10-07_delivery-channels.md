# 🔬 분석: 발송 채널 (메일·문자·카카오톡)

## 개정 (2026-10-07) — 메일 발송 수단을 SES 에서 Gmail SMTP 로 변경
- **무엇이 깨졌나**: 아래 전제 "발신에 쓸 도메인이 있거나 새로 마련할 수 있다"가 깨졌다. 사용자가 발신 도메인이 없다고 답했다.
- **새 선택**: 메일은 그대로 1차 채널이다. 발송 수단만 **발송 전용 Gmail 계정 + 앱 비밀번호로 `smtp.gmail.com:587`** 로 바꾼다. 사용자가 선택했다. 근거 자료는 [[2026-10-07_gmail-smtp-sending]].
- **고른 이유**: 비용이 없고 표준 라이브러리만으로 된다. 일 500통 한도는 예상 사용량(하루 2회 × 10명 이하)의 25배 이상이다. Gmail 서버가 직접 보내므로 @gmail.com 발신이 정상 경로다.
- **버린 것**
  - 도메인 구입 + SES: 인증이 만료되지 않고 확장에 유리하지만, 상업화 목표가 없는 단계에서 연 비용과 DNS 설정을 들일 이유가 약하다. 수신자가 늘면 다시 본다.
  - 개인 Gmail 주소를 SES 발신자로 검증: Google 발신자 가이드라인이 Gmail 밖에서 @gmail.com 을 From 으로 쓰는 것을 격리 대상으로 적는다.
  - Gmail API + OAuth: 동의 화면이 Testing 상태면 refresh token 이 7일 뒤 만료된다. 자동 발송에 맞지 않는다.
  - SMTP + XOAUTH2: Restricted 스코프가 필요하다.
  - 평소 쓰는 개인 계정을 발신자로: 앱 비밀번호는 계정 전체 메일에 접근할 수 있는 비밀값이다. 전용 계정이면 유출·차단의 영향이 그 계정에 갇힌다.
- **새 전제 (깨지면 재검토)**
  - 앱 비밀번호가 개인 계정에서 계속 발급·사용된다. Google 은 "권장하지 않는다"고 적지만 폐지 일정은 공지하지 않았다.
  - AWS 호스트에서의 SMTP 로그인이 "새 위치"로 차단되지 않는다. 공식 안내로는 확인하지 못했고 PoC 로만 확인할 수 있다. 차단되면 도메인 + SES 로 돌아간다.
  - 하루 발송량이 500통에 한참 못 미친다.
- **새 리스크**
  - 계정 비밀번호를 바꾸면 앱 비밀번호가 폐기돼 발송이 조용히 멈춘다 → 인증 실패 시 작업이 실패로 끝나고 로그·알람으로 드러나게 한다. 실패 알림은 메일 경로로 보낼 수 없다.
  - 앱 비밀번호 유출 → SSM Parameter Store 에만 두고, 전용 계정에는 다른 용도의 메일을 두지 않는다.
- **이 개정으로 무효가 된 아래 내용**: 결론의 "Amazon SES", 이유 3번, 옵션 표의 SES 열에 대한 선택, SES 샌드박스·서울 리전 전제, "SendGrid·Mailgun·Resend 를 버린 이유"의 SES 비교. 나머지(채널 순서, 알림톡·브랜드 메시지 배제, 트리거·중복 방지)는 그대로다.

## 결론 (먼저)
- **선택**
  - **1차 채널은 메일(Amazon SES)** 이다. 브리핑 전문은 메일로 보낸다.
  - **2차 채널은 카카오톡 "나에게 보내기"** 다. 수신자 각자가 카카오 로그인으로 동의하고, 서버가 그 사람의 토큰으로 본인에게 보낸다. 메일이 안정된 뒤 붙인다.
  - **문자는 지금 붙이지 않는다.** 채널은 `Notifier` 인터페이스 뒤에 두어 나중에 추가할 수 있게 한다.
  - **알림톡·브랜드 메시지는 쓰지 않는다.**
  - 트리거는 **EventBridge Scheduler 로 일 2회**, 중복 발송 방지는 **DB 의 발송 기록(날짜·슬롯·수신자·채널)** 으로 한다.
- **이유 3줄**
  1. 알림톡과 브랜드 메시지는 비즈니스 채널(사업자)이 선행 조건이고, 알림톡은 무료 구독형 메시지를 명시적으로 불가로 둔다. 사업자등록이 없는 무료 서비스는 둘 다 쓸 수 없다.
  2. 미국 개장 시각은 한국 시간 밤이다. 메일은 야간 전송 제한의 제외 매체이고 길이 제한도 없어 LLM 요약 전문을 그대로 실을 수 있다.
  3. SES 는 1,000통당 0.16 USD 이고 이미 쓰는 AWS 계정·IAM 안에서 끝난다. 수신자가 소수라 샌드박스 한도(24시간 200통) 안에서도 돌아간다.

## 문제 분해
1. **채널 자격**: 사업자등록 없이, 무료 구독으로 쓸 수 있는 채널이 무엇인가.
2. **내용 적합성**: LLM 요약 브리핑이 채널의 길이·형식 제한 안에 들어가는가.
3. **발송 시각**: 미국 개장은 한국 시간 22:30(서머타임) 또는 23:30 이다. 야간 제한에 걸리는 채널이 있는가.
4. **비용**: 수신자 소수 × 하루 2회.
5. **트리거와 중복 방지**: 태스크가 항상 2개 이상 도는 구조에서 정해진 시각에 한 번만 보내는 방법.

## 버린 옵션과 이유
- **알림톡**: 비즈니스 채널 전환이 선행 조건이고 그 서류가 사업자 기준이다. 또 카카오 발송 예시가 "무료 뉴스레터 등 무료 구독형 메시지 불가", "비 제도권금융회사에서 발송하는 주식 종목 추천 메시지 발송 불가"라고 적는다. 자격과 내용 양쪽에서 막힌다.
- **브랜드 메시지**: 비즈니스 채널이 필요하고, 발송 가능 시간이 08:00~20:50 이라 미국 개장 브리핑(22:30/23:30)을 보낼 수 없다. 광고 메시지 상품이라 성격도 맞지 않는다.
- **카카오톡 친구에게 보내기**: 비즈 앱 전환과 비즈니스 정보 심사가 필요하고 1회 5명 제한이 있다. 용도도 "서로간 상호작용 목적"이다. 같은 결과를 "나에게 보내기"로 심사 없이 얻을 수 있다.
- **문자(지금은 보류)**: 건당 과금이 있는 유일한 후보이고, LMS 2,000바이트(한글 약 1,000자)에 LLM 요약과 링크를 다 넣기 어렵다. 발신번호 등록 절차도 필요하다. 메일과 카카오톡으로 부족할 때 "브리핑 도착" 한 줄 알림 용도로 다시 본다.
- **AWS End User Messaging / Twilio 문자**: 한국은 국제 발신만 되고 Sender ID 가 지원되지 않는다. Twilio 는 "[국제발신]" 이 붙고 장문이 분할된다. 국내 딜러사보다 나은 점이 없다.
- **SendGrid·Mailgun·Resend**: 무료 한도는 충분하지만 외부 계정과 API 키가 하나 더 생긴다. SES 는 태스크 역할에 정책만 붙이면 되고 키를 저장할 필요가 없다.
- **스티비**: 무료 플랜이 월 2회 발송이라 하루 2회 발송에 맞지 않는다.
- **앱 내부 스케줄러**: 이 서비스는 태스크가 2개 이상 동시에 돌고 예고 없이 교체된다. 프로세스마다 스케줄러가 깨어나므로 잠금이 필수가 되고, 잠금이 정확성의 유일한 방어선이 된다. 외부에서 한 번 호출하는 쪽이 구조가 단순하다.

## 전제 (깨지면 재검토)
- **수신자는 본인과 소수의 특정 지인이고, 각자 직접 받겠다고 한 사람이다.** 공개 구독을 받으면 수신동의 기록·수신거부·2년 재확인, Gmail 대량 발신자 요건, SES 샌드박스 해제가 모두 필요해진다.
- **이 브리핑은 "영리목적 광고성 정보"가 아니다.** 운영 주체가 개인이고 무료이며 홍보가 없다는 조건에서 그렇게 본다. KISA 안내서 원문은 리서치에서 확인하지 못했으므로 이것은 가정이다. 광고·제휴 링크를 넣거나 사업자가 되면 깨진다.
- **발신에 쓸 도메인이 있거나 새로 마련할 수 있다.** 없으면 개인 메일 주소를 발신 아이덴티티로 검증해 보낼 수 있지만 수신함 도달이 나빠질 수 있다. → 사용자 확인 필요.
- SES 샌드박스는 검증된 주소로만 보낼 수 있다. 수신자 각자가 검증 메일의 링크를 한 번 눌러야 한다. 이 불편이 싫으면 프로덕션 액세스를 신청한다.
- SES 가 ap-northeast-2 에서 쓸 수 있다. 리서치는 2020년 발표 제목만 확인했다.
- EventBridge Scheduler 가 시간대(America/New_York)를 지정한 일정을 지원해 서머타임을 따라간다. 리서치 범위 밖이라 플랜에서 확인한다.
- 카카오 "나에게 보내기"의 토큰 유효기간·갱신 조건과 메시지 길이 제한은 리서치에서 확인하지 못했다. 2차 채널을 붙일 때 먼저 조사한다.

## 플랜 단계로 넘기는 것
- 발신 도메인 유무 확인 (사용자).
- 발송 시각의 정확한 정의: 개장 정각인지, 개장 몇 분 전인지.
- 수신자 저장 모델 (주소, 채널, 카카오 토큰). 스키마 변경은 하위 호환으로.
- 발송 작업의 실행 형태: 서비스의 내부 엔드포인트 호출인지, 일회성 ECS 태스크인지.
