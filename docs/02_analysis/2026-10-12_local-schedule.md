# 🔬 분석: 로컬 스케줄 — delivery-channels Task 8 을 로컬 방식으로 다시 정한다

## 결론 (먼저)
- **선택**: **A. Windows 작업 스케줄러** 두 항목(`finbrief-kr-open`, `finbrief-us-open`)이 저장소 안의 런처를 부른다. 미국 슬롯은 **22:30 KST 한 시각**으로 고정한다. 놓친 실행은 `StartWhenAvailable` 로 PC 가 깨어나면 바로 돌린다. 실패는 결과 코드 + 슬롯별 로그 + 기존 운영자 메일로 드러낸다.
- **이유 3줄**:
  1. 이 PC 는 노트북이고 5분이면 대기 상태가 된다. 상주 프로세스(B·C)는 PC 와 함께 잠들고 깨우지 못하지만, 작업 스케줄러는 깨우기를 시도하고 깨어난 뒤라도 실행한다.
  2. 코드 변경이 없다. 발송 작업은 이미 한 번 실행·종료 코드·중복 방지를 갖춘 명령이다. 필요한 것은 "누가 부르는가"뿐이다.
  3. 사용자가 같은 PC 에서 같은 방식(`jandi-picker`)을 이미 쓴다. 보는 곳이 한 곳이다.

## 문제 분해
1. **트리거** — 정해진 시각에 `run_briefing --slot X` 를 누가 부르는가.
2. **시간대** — ET 09:30 을 KST 밖에 모르는 트리거로 어떻게 표현하는가.
3. **놓친 실행** — PC 가 대기·꺼짐이었다가 몇 시간 뒤 켜지면 보내는가.
4. **비밀값** — 로컬에서 `.env` 를 어떻게 다루는가.
5. **실패 알람** — 메일이 안 왔을 때 어디를 보면 이유가 있는가.
6. **정리** — 저장소 밖의 런처 사본과 실패한 일회성 작업을 어떻게 하는가.

## 옵션 비교 (1. 트리거)
| | A: 작업 스케줄러 | B: APScheduler 상주 프로세스 |
|---|---|---|
| 구현 비용 | 런처(`.cmd`) + 등록 스크립트(`.ps1`) 2개. 코드·의존성 변경 없음 | 스케줄러 모듈·진입점·compose 서비스·테스트. 의존성 1개 |
| 운영 비용 | 없음. 로그인만 돼 있으면 된다 | Docker Desktop + 컨테이너 1개가 늘 떠 있어야 한다 |
| PC 대기 상태 | `WakeToRun` 시도 + `StartWhenAvailable` 로 깨어나면 실행 | 깨우지 못한다. 깨어난 뒤 `misfire_grace_time` 안이면 실행 |
| 시간대 | KST 고정 시각만 (아래 2 에서 처리) | IANA 시간대 그대로 |
| 리스크 | 예정 시각에 PC 가 안 깨면 늦게 간다 | 같은 리스크 + 컨테이너가 죽어 있으면 아무 일도 없다 |
| 되돌리기 | 쉬움 (`Unregister-ScheduledTask`) | 보통 (서비스·의존성 제거) |

## 나머지 결정
### 2. 시간대 — us_open 은 22:30 KST 하나
- 22:30 KST = 09:30 EDT(3~11월) / 08:30 EST(11~3월). 겨울에 한 시간 이르다.
- 미국 개장 브리핑이 전하는 것은 간밤의 국내·아시아 시장과 미국 전일 종가다. 08:30 ET 에도 내용이 같다. "개장 전에 받는다"는 오히려 플랜의 열린 질문("개장 전에 받고 싶으면 스케줄 식만 바꾸면 된다")과 맞는다.
- 두 시각(22:30·23:30)을 걸면 겨울엔 둘 다 돌아 두 번째가 수집을 다시 한다(Marketaux 하루 100회). "이미 받은 경우 수집 생략"을 먼저 고쳐야 하는데, 그 수정은 이 결정과 무관하게 따로 할 가치가 있으니 선행 조건으로 묶지 않는다.
- 작업 안에서 ET 를 판정하는 방식은 코드가 늘고, 결국 트리거는 두 개여야 한다. 버린다.

### 3. 놓친 실행 — 보낸다 (`StartWhenAvailable`)
- 늦은 브리핑이 없는 브리핑보다 낫다. 데이터는 실행 시점에 다시 수집하므로 내용은 늦은 만큼 더 새롭다.
- `brief_date` 가 슬롯 시간대의 날짜라, 다음 날 아침에 PC 가 켜져 us_open 이 돌면 ET 로는 아직 전날이어서 **전날 날짜의 브리핑**이 간다. 메일 제목 날짜가 하루 어긋나 보일 수 있다. 자주 생기면 "예정 시각에서 N시간 지나면 보내지 않는다" 창을 런처 또는 작업에 둔다. 지금은 두지 않는다.
- `MultipleInstancesPolicy=IgnoreNew`, 실행 제한은 **30분**(오늘 kr_open 은 3분 35초. 첫 미국 이력 받기는 `screen_update_seconds`=240초 상한이 있다. 20분이던 일회성 작업은 중단됐다).

### 4. 비밀값 — `.env` 그대로
- `.env` 는 git 에서 제외돼 있고 Windows 사용자 계정 안에 있다. `SecretStr` 로 읽어 로그에 남지 않는다. 로컬 단일 사용자 PC 에서 SSM 의 대체물은 이것으로 충분하다.
- 런처는 작업 디렉터리를 저장소로 맞춘다(`env_file=".env"` 가 현재 디렉터리를 본다). 런처·로그·문서에 값이 들어가지 않는다.

### 5. 실패 알람 — 결과 코드 + 로그 + 운영자 메일. 토스트는 보류
- 작업의 종료 코드가 작업 스케줄러의 "마지막 실행 결과"가 된다. 런처는 작업의 종료 코드를 그대로 돌려줘야 한다(현재 `.cmd` 는 `echo` 가 마지막이라 항상 0 — 고친다).
- 슬롯별 로그(`logs/<slot>.log`)는 **저장소 안** `logs/` (git 제외)에 둔다. `jandi-picker` 와 같은 자리다.
- 아무도 못 받은 날은 이미 운영자 메일이 간다(`operator_email`). SMTP 자체가 깨진 날은 메일로 알릴 수 없고 결과 코드 1 로만 남는다 — 이 한계는 원래 분석과 같다.
- Windows 토스트는 Home 에디션에 `msg.exe` 가 없고 PowerShell 모듈이 필요하다. 메일이 하루 안 오면 사람이 알아채는 구조라 지금은 넣지 않는다.

### 6. 정리
- 런처를 `scripts/run_briefing.cmd` 로 저장소에 넣고, `AppData\Local\finbrief\run_briefing.cmd` 는 지운다.
- `finbrief-us-open-once` 는 등록 스크립트가 지운다(실패한 실험, 문서 없음).
- 등록 스크립트 `scripts/register_tasks.ps1` 는 두 항목을 **멱등**으로 만든다(있으면 덮어쓴다). 해제 스크립트 또는 `-Unregister` 스위치를 둔다.

## 버린 옵션과 이유
- **B(APScheduler 상주)를 버린 이유**: 이 PC 에서는 프로세스가 PC 와 함께 잠든다. 시간대 표현이 깔끔한 것 하나로 코드·의존성·상주 컨테이너를 더하는 값을 못 한다. 나중에 늘 켜진 호스트가 생기면 그때 다시 본다.
- **C(컨테이너 cron)를 버린 이유**: B 의 단점에 이미지가 하나 더 는다.
- **us_open 두 시각**을 버린 이유: 수집 중복과 선행 수정이 생긴다. 겨울 한 시간 이른 발송은 내용상 손해가 없다.

## 전제 (깨지면 재검토)
- 사용자는 평일 아침 09:00 KST 와 밤 22:30 KST 전후에 이 노트북에 **로그인된 채** 두거나, 그 뒤 몇 시간 안에 연다. (로그인 전·전원 꺼짐에서는 어느 옵션도 돌지 않는다.)
- Docker Desktop 이 로그인 시 자동 시작된다(현재 Run 키에 있음).
- 브리핑은 "개장 직후"가 아니라 "개장 무렵"에 오면 된다.

## 리스크와 완화
| 리스크 | 가능성 | 영향 | 완화 |
|---|---|---|---|
| 예정 시각에 PC 가 대기 상태이고 `WakeToRun` 이 못 깨운다 | 높음 (`jandi-picker` 가 11시간 늦었다) | 늦은 브리핑 | `StartWhenAvailable`. 늦어도 보낸다 |
| 로그인 직후 Docker 엔진이 아직 안 떠서 `compose up --wait` 실패 | 중간 | 그 슬롯 결과 코드 ≠ 0, 발송 안 됨 | 런처에서 엔진 준비를 최대 2분 기다린다(`docker info` 재시도) |
| 다음 날 아침에 켜져 전날 날짜의 us_open 이 간다 | 낮음 | 제목 날짜 혼동 | 반복되면 발송 창(N시간) 추가 |
| 런처 인용 오류로 작업이 시작도 못 한다 (`267014` 의 유력 원인) | 중간 | 조용히 실패 | 등록 직후 `Start-ScheduledTask` 로 수동 1회 실행해 로그·결과 코드 확인을 완료 판정에 넣는다 |
| 겨울에 ET 08:30 발송 | 확정 | 없음(내용 동일) | 문서에 명시 |
