# 🔍 리서치 모드

지금부터 **리서치 모드**다. 코드를 쓰지 않고, 결론도 내리지 않는다.

## 목표
`$ARGUMENTS` 에 대해 판단에 필요한 재료를 모은다. "무엇이 있는가" 까지만.

## 절차

0. **단계 선언** — `.claude/hooks/harness.py stage research` 를 먼저 실행한다.
   이 시점부터 훅이 `docs/` 밖 편집을 차단한다.

1. **범위 확정**
   - 이 리서치가 답하려는 핵심 질문 1줄을 확정하고 사용자에게 보여준다.
   - 질문이 2개 이상으로 갈리면 노트를 나눈다. 한 노트 = 한 질문.

2. **서브에이전트로 병렬 조사** — 이 단계의 핵심이다.

   리서치는 **컨텍스트를 가장 많이 더럽히는 단계**다. 파일 수십 개와 웹 문서
   수십 장을 본문째 메인 컨텍스트에 올리면, 정작 판단할 때 쓸 자리가 남지 않는다.
   그래서 **조사는 서브에이전트에게 맡기고, 요약만 받는다.**

   아래 3축을 **한 메시지에서 동시에** 띄운다 (순차 실행 금지 — 서로 의존이 없다).

   | 축 | 에이전트 | 무엇을 |
   |---|---|---|
   | A. 코드베이스 | `Explore` | 이미 비슷한 게 있는지. 있으면 어디에, 어떤 모양으로 |
   | B. 외부 | `general-purpose` | 공식 문서 우선, 블로그는 보조. **버전 명시 필수** |
   | C. 이력 | `general-purpose` | `git log`, 관련 이슈·PR. 과거에 시도했다 접은 방식 |

   각 서브에이전트에게 **반드시 다음을 요구한다**:
   - 출력은 **30줄 이내**. 파일 본문·웹 본문을 그대로 붙여오지 말 것.
   - 모든 주장에 **출처**(파일:줄 또는 URL). 출처 없는 문장은 빼라고 지시.
   - **결론·추천 금지.** 사실만. 판단은 분석 단계 몫이다.
   - 확인 못 한 것은 "확인 못 함" 으로 명시.

   축이 2개 이하로 충분한 주제면 굳이 3개를 띄우지 않는다.
   반대로 조사 범위가 넓으면 축 B 를 주제별로 더 쪼개도 된다.

3. **메인 컨텍스트에서는 종합만 한다**
   - 서브에이전트 요약 3장을 놓고 **겹치는 것·엇갈리는 것**을 정리한다.
   - **엇갈리면 그대로 적는다.** 한쪽으로 몰아서 매끄럽게 만들지 않는다.
   - 요약만으로 판단이 안 서는 지점이 있으면, 그 지점만 직접 원문을 확인한다.
     이때도 필요한 부분만 읽는다.

4. **기록** — `docs/01_research/YYYY-MM-DD_<slug>.md`
   - 양식은 `docs/00_templates/research.md` 를 따른다.
   - `status` 는 미해결 질문이 남아 있으면 `draft`, 다 채웠으면 `done`.

5. **마무리**
   - 저장 경로 출력.
   - 열린 질문 목록을 다시 보여주고 `/analyze <파일명>` 을 제안한다.

## 제약
- 코드 작성·파일 수정 **금지** (리서치 노트 자체는 예외). 훅이 강제한다.
- "A 가 낫다" 류의 결론 **금지**. 그건 분석 단계 몫이다.
- 확인 못 한 것은 "확인 못 함" 으로 남긴다. 추측으로 빈칸을 메우지 않는다.
- **서브에이전트가 가져온 요약을 그대로 믿지 않는다.** 결정을 좌우할 사실이면
  출처를 직접 확인한다. 특히 버전·수치·API 시그니처.
