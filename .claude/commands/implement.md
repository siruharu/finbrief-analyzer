# 🛠️ 구현 모드

**유일하게 파일을 바꾸는 모드다.**

## 절차

0. **단계 선언** — `.claude/hooks/harness.py stage implement <주제>` 를 먼저 실행한다.
   편집 게이트가 풀리고, 대신 **종료 게이트가 켜진다** (아래 5번).

1. **다음 할 일 조회** — 문서를 파싱하지 않는다. 물어본다.

   ```bash
   .claude/hooks/harness.py task next
   ```

   - 태스크가 없다고 나오면 멈추고 `/task` 를 먼저 요구한다.
   - 설계 의도는 `docs/04_tasks/<주제>.md` 에서 읽는다.
   - 고른 Task 를 보여주고 "이걸 구현할까요?" 확인받은 뒤 `task start <id>`.

2. **한 번에 하나**
   - `git status` 로 작업 트리가 깨끗한지 확인한다. 더러우면 먼저 정리를 제안한다.
   - Task 전용 브랜치가 아니면 브랜치를 판다.

3. **TDD**
   - 테스트 먼저 → **실패를 눈으로 확인** → 최소 구현 → 통과 → 리팩터.
   - 테스트를 건너뛰고 싶으면 그 이유를 구현 노트에 적는다. 조용히 넘어가지 않는다.
   - 코딩 규칙은 이 저장소 `CLAUDE.md` 를 따른다.

4. **녹색이 될 때까지 반복** — 이 단계가 루프다.

   ```
   편집 → 훅이 그 파일을 즉시 검증 (실패하면 바로 되돌아온다)
        → 검증 명령 전체 실행
        → 실패? 출력을 읽고 원인부터 파악 → 다시 편집
        → 통과할 때까지
   ```

   - **실패 출력을 읽지 않고 다시 편집하지 않는다.** 추측 수정이 가장 흔한 시간 낭비다.
   - 같은 실패를 3번 못 고치면 멈추고 사용자에게 무엇이 왜 막히는지 보고한다.
     혼자 더 파는 것보다 그게 싸다.
   - 통과하면 커밋. Task 1개 = 커밋 1개. Conventional Commits, subject 는 한국어.
   - 커밋 후 `task done <id>`. **이건 선언이 아니라 판정이다** — 하네스가 그 Task 의
     `verify` 명령을 다시 돌리고, 실패하면 완료 처리를 거부한다. 거부당하면 고치고 다시 한다.
   - 못 푸는 상태면 `task block <id> "이유"` 로 표시하고 다음으로 넘어가거나 상의한다.

5. **종료 게이트**
   - `Stop` 훅이 변경분에 대해 검증 명령을 다시 돌린다. **실패하면 세션을 끝낼 수 없다.**
   - 이건 우회 대상이 아니라 안전장치다. 통과 못 한 걸 통과했다고 말하지 않는다.
   - 정말 못 고치는 상황이면 사용자에게 보고한다. `HARNESS_SKIP=1` 은 사용자가 정한다.

6. **기록** — `docs/05_implementation/YYYY-MM-DD_<slug>.md` (양식: `docs/00_templates/implementation.md`)
   - diff 요약이 아니라 **왜 그렇게 했는지**를 쓴다. diff 는 git 이 이미 갖고 있다.
   - **막혔다가 푼 지점은 과정까지 상세히** 쓴다. 이게 블로그 글의 원재료다. 있으면 frontmatter 에 `blog_candidate: true`.
   - 구현 중 발견한 별개 문제는 `발견한 이슈` 에 적고 진행한다. 중대하면 멈추고 상의한다.

7. **남은 일 확인** — `task list` 로 진행 상황을 보여준다. 수동으로 상태 파일을 고치지 않는다.

8. **마무리** — 변경 파일 / 커밋 해시 / 검증 결과 / 남은 Task 수. 블로그 소재는 `💡` 로 표시.

## 제약
- 플랜에 없는 기능 임의 추가 **금지**. 필요하면 플랜으로 되돌아간다.
- 한 번에 여러 Task 를 섞지 않는다. 리뷰가 불가능해진다.
- "동작하겠지" 금지. 돌려보고 말한다.
- **훅을 끄고 진행하지 않는다.** `HARNESS_SKIP=1` 은 사용자만 쓴다.
